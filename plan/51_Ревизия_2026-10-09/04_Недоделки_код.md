## Находки

### P1-1 — Уровень сложности меняет глобальный `CONFIG` для всех живых партий сервера
- **Где:** `src/server/sessions.ts:74` (`applyDifficulty(difficulty); // M6: уровень — до newGame`), `src/server/sessions.ts:97-100` (`applyDifficulty(isDifficultyId(saved) ? saved : 'normal')`), `src/core/difficulty.ts:74-81` (`applyDifficulty` пишет в живой `CONFIG`), `src/core/systems/dev.ts:273,280`, `src/core/formulas.ts:27`, `src/core/systems/progression.ts:442-445` (чтение `CONFIG` в момент тика), `test/difficulty.test.ts:2-3` («CONFIG — один изменяемый объект»).
- **Что:** `CONFIG` — единственный мутируемый объект на процесс; уровень партии применяется к нему в момент `sessions.create()` и `sessions.load()`. Каждая сессия (`SessionRegistry.live`, `sessions.ts:60`) держит свой `GameServer` со своим тикером. Игрок A на «сложном», игрок B на «лёгком»: кто последним открыл сохранение — тот и задал `DEV_COST_SCALE`, `BLACKOUT_CHANCE`, `START_MONEY`, `CONTRACT_WEEKLY_RATE` для **обеих** партий. Поле `game.difficulty` при этом чисто информационное: в тике оно не читается нигде (весь `grep .difficulty` по `src` — только сохранения/UI).
- **Последствие:** скрытое и необратимое расхождение баланса у игроков (стоимость разработки, шансы аварий, доход с контрактов), которое невозможно воспроизвести по сейву; тесты этого не ловят (тестируется одна сессия за раз).
- **Действие:** либо сделать уровень частью сессии (читать конфиг уровня из `game.difficulty` в тех же точках, где сейчас читается `CONFIG`, через `difficultyConfig(game.difficulty)`), либо запретить совместную работу партий разных уровней и документировать это в `plan/36`; добавить тест «две сессии с разными уровнями — числа не пересекаются». (L)

### P1-2 — Проверка TLS отключена, при этом в том же соединении уходит клиентский секрет GigaChat
- **Где:** `src/server/giga.ts:44` — `https.request(url, { method: 'POST', headers, rejectUnauthorized: false }, ...)`; вызов OAuth: `src/server/giga.ts:61-66` — POST на `https://ngw.devices.sberbank.ru:9443/api/v2/oauth` с заголовком `Authorization: Basic base64(id:secret)`; все остальные вызовы — `src/server/giga.ts:82`.
- **Что:** `rejectUnauthorized: false` действует на **все** вызовы `gigaPost`, включая обмен OAuth-токена, где передаётся `GIGACHAT_CLIENT_SECRET`. Причина (самоподписанный корень Сбера) описана в комментарии `src/server/giga.ts:2` и в plan/13 A9, но решение выбрано самым слабым способом: проверка сертификата сервера отключена полностью.
- **Последствие:** MITM в любом месте между VDSina и Сбером получает `client_id`/`client_secret` (доступ к платному API от имени владельца) и может подменять ответы LLM (тексты чата, письма, названия). Секреты утекают «на уровне транспорта», не из БД.
- **Действие:** добавить доверенный корень (Russian Trusted Root/Sub CA) в хранилище или передавать его через `ca:` в `https.request`, вернув `rejectUnauthorized: true`; до этого — как минимум отдельный `gigaPost` для OAuth с проверкой сертификата. (S/M)

### P1-4 — Нет лимитов на число сохранений, размер payload и личные сообщения → рост `users.db` и блокировка event loop
- **Где:** `src/server/api.ts:341-388` (`POST /api/saves` — любой авторизованный пользователь создаёт сохранение без ограничения количества), `src/server/users.ts:575-581` (`createSave` — простой `INSERT`), `src/core/migrate.ts:115-127` (`isValidGameState` проверяет только типы `week/year/money/fans/research` и наличие массивов `staff`/`history`; размер и лишние поля не ограничены), `src/server/server.ts:40` (`express.json({ limit: '8mb' })`), `src/server/users.ts:438-468` (`leaderboard()` синхронно `JSON.parse` **всех** payload’ов всех сохранений, кеш 60 с), `src/server/users.ts:530-532` + `src/server/api.ts:266-275` (`dmSend` — без лимита и без rate-limit на `/api/dm/:userId`).
- **Что:** инвайт-игрок может циклом создавать сохранения (каждое — валидное по структуре, до ~8 МБ) и слать неограниченные DM (до 1000 символов каждый). Ни `createSave`, ни `dmSend` не имеют ни квоты, ни TTL, ни чистки. Первый же запрос `/api/leaderboard` после роста БД парсит все payload’ы синхронно.
- **Последствие:** диск VDSina (единственный, тариф без бэкапов) заполняется любым зарегистрированным игроком; при нескольких тысячах сохранений `/api/leaderboard` замораживает event loop — встают тикеры **всех** игроков (плюс окно продаж дергает его регулярно).
- **Действие:** квота сохранений на пользователя (например, 10) и лимит размера payload; заменить полный скан на лёгкий индекс (таблица-витрина, обновляемая при релизе) или вынести разбор из запроса; rate-limit на `/api/dm`. (M)

### P2-1 — Сброс пароля: `reset-confirm` без rate-limit и с непостоянным сравнением кода
- **Где:** `src/server/api.ts:181-192` (`app.post('/api/auth/reset-confirm', ...)` — лимитов нет; в `reset-request` лимит есть, `src/server/api.ts:167`), `src/server/users.ts:288-290` (код — 6 цифр, `randomInt(100000, 999999)`), `src/server/users.ts:299` (`if (row.code_hash !== sha256(...)) return ...` — сравнение строк `!==`, тогда как пароли сравниваются `timingSafeEqual`, `src/server/users.ts:91`).
- **Что:** на `reset-confirm` не действует ни `loginLimit`, ни отдельный счётчик; сравнение хэшей — обычное.
- **Последствие:** при включённом `PASSWORD_RESET=1` (не прод-дефолт, но переключатель есть) 6-значный код (10^6) перебирается за минуты при 15-минутном окне `RESET_MS`; успех = смена пароля жертвы и разлогин всех сессий.
- **Действие:** добавить `RateLimit` на `reset-confirm` (например, 5/15 мин на login+IP) и сравнивать хэши через `timingSafeEqual` над буферами. (S)

### P2-2 — Прод-гейт конфигурации обходится через `NODE_ENV=production`
- **Где:** `src/server/server.ts:53` — `if (process.env.PROD === '1' && !process.env.GDS_PEPPER)` против `src/server/config.ts:21` — `export const PROD = process.env.PROD === '1' || process.env.NODE_ENV === 'production';`.
- **Что:** модуль конфига считает прод-режимом и `NODE_ENV=production`, а проверка «в проде обязателен перец» смотрит только на сырой `process.env.PROD`. `.env.example` описывает `PROD=1`, но systemd/хостинг может выставлять `NODE_ENV`.
- **Последствие:** развёртывание с `NODE_ENV=production` и без `PROD=1` стартует без перца: `PASSWORD_RESET` при этом выключается (правильно), но пароли в `users.db` остаются «бесперечными» — при утечке файла БД (а она лежит в каталоге, который деплой и бэкапы копируют) перебор scrypt-хэшей резко дешевле.
- **Действие:** использовать в проверке импортированный `PROD` из `./config` (и добавить туда же проверку `GDS_OWNER_PASSWORD` из P1-3). (S)

### P2-3 — `pnpm db:build` удаляет рабочую БД до сборки; нет проверки версии/наличия БД
- **Где:** `tools/build-db.ts:453-455` — `mkdirSync(...); rmSync(DB_PATH, { force: true }); // всегда пересоздаём с нуля; const db = new DatabaseSync(DB_PATH);`; `src/core/data/db.ts:15` — `const db = new DatabaseSync(DB_PATH, { readOnly: true });` (на уровне импорта модуля), `src/core/data/db.ts:211-215` — `dbInfo()` c `PRAGMA user_version` (никем не вызывается).
