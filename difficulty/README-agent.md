# Уровни сложности: задание для агента и происхождение чисел

Этот файл — **задание и контекст**, а не код. Рядом лежит `difficulty-presets.json` — сами числа.
Прочитай оба, потом делай.

---

## 1. Кто написал и зачем

Файл написал **Hermes** — агент [лаборатории баланса GDS](file:///E:/My/gds-autoresearch)
(`E:/My/gds-autoresearch`, мини-версия [autoresearch](https://github.com/karpathy/autoresearch) Карпатого,
пересаженная на экономику этой игры). Лаборатория **не пишет в репозиторий игры**: она гоняет
экономику в памяти (импортирует ядро игры напрямую), ищет значения ручек `CONFIG` и меряет
числом «насколько экономика сломана». Числа в `difficulty-presets.json` — результат такого поиска,
а не ручная подгонка.

Человек (владелец проекта) принял решение: **в игре должно быть три уровня сложности**. Твоя задача —
механика: сделать уровни в самой игре и отрефакторить её так, чтобы уровни были честной частью
системы, а не костылём. Балансные числа уже найдены — их не надо придумывать заново (и не надо
«улучшать» по вкусу: они проверены замером).

## 2. Что за файлы

| Файл | Что внутри |
|---|---|
| `difficulty/README-agent.md` | этот файл: контекст, задание, ограничения, приёмка |
| `difficulty/difficulty-presets.json` | три уровня: `overrides` (отличия от базового `CONFIG`), `fullConfig` (полный набор значений), правила уровня (`mayFail`), блок `source` с происхождением чисел |

`overrides` — рекомендуемая форма для игры: уровень = базовый `CONFIG`, перекрытый `overrides`.
`fullConfig` — те же значения целиком (для проверки и воспроизведения).

## 3. Откуда взялись числа

Коротко: их нашёл поиск по метрике, которую человек задал как «что такое хороший баланс».

- **Метрика «дисбаланс»** (меньше = лучше): сумма по уровням сложности × 5 стилям игрока × 8 сидам.
  Каждый стиль (разумный, жадный, случайный, бездельник, багофил) прогоняется автопилотом игры,
  и штрафуется за нарушения ожиданий: банкротства, хрупкость (остаток денег ниже порога),
  коридор денег к концу партии, темп релизов, рост мастерства, балл прессы, тираж первой игры.
- **Проверка лестницы:** у одного и того же игрока на «сложном» не должно быть легче, чем на
  «нормальном» (больше денег, выше балл, меньше разорений). Иначе три уровня сложности — фикция.
- **Протокол v5:** 8 сидов × **7300 дней (20 игровых лет)**, детерминированно: один сид + один набор
  значений = один и тот же результат. Все числа в JSON получены на этих 20 годах.
- **Почему 20 лет:** на двух годах меряется только фаза выживания; долгая партия проверяет, что
  уровни и экономика держатся всю игру (см. §7 — там важное предупреждение про инфляцию).

Детали, полные таблицы «игрок × уровень», история экспериментов и инструкция по перезапуску поиска —
в лаборатории: `E:/My/gds-autoresearch/results/report.md`, README и скилл `gds-autoresearch`.

## 4. Что нужно сделать

1. **Ввести понятие уровня сложности в ядро игры** (`src/core/`): три уровня — `easy`, `normal`, `hard`
   (человекочитаемые названия и подписи — в JSON: `label`, `note`).
2. **Применение уровня = наложение `overrides` на базовый `CONFIG`.** Не три копии конфига,
   а база + перекрытия: так уровни не расползаются при будущих правках баланса.
3. **Дать возможность выбрать уровень** в UI: на старте новой игры (как в оригинальной Game Dev Story)
   и/или в настройках. Выбор должен быть виден игроку, а не спрятан.
4. **Сохранять выбранный уровень** в сохранении (см. `plan/18_Пользователи_и_сохранения.md`): загрузка
   игры обязана восстановить тот же уровень; смена уровня посреди партии — либо запрещена, либо
   явная и осознанная (реши сам и опиши в `plan/`, но не делай её незаметной).
5. **Отрефакторить** то, что мешает: если сейчас есть места, которые читают `CONFIG` один раз при
   импорте модуля (кэшируют производные значения, замыкают константы), — перевести их на чтение
   в момент вызова. Иначе уровень, применённый к живому `CONFIG`, не подействует на часть систем.
6. **Документировать**: коротко в `README.md` (что такое уровни, где живут числа) и, если меняешь
   правила игры, — в `plan/` (там уже есть `plan/08_Экономика_и_баланс.md`).

## 5. Жёсткие ограничения (это контракт с лабораторией — иначе она сломается)

Лаборатория импортирует ядро игры напрямую по относительному пути `../../GameDevStory/src/core/...`.
Фактические импорты (файл `E:/My/gds-autoresearch/harness/gds.ts`) — **их нельзя ломать**:

```ts
// src/core/engine.ts
export { newGame, tick, startProjectAction, hireAction, buyAdAction, moveOfficeAction, releaseAction }
// src/core/sim/policy.ts
export { createPlayer, resolvePendingEvent, autopilotProjectInput }
export type { PolicyStats, ScriptedPlayer }
// src/core/config.ts
export { CONFIG }
// src/core/types.ts
export type { GameRecord, GameState, StartProjectInput }
```

Правила, которые из этого следуют:

1. **`CONFIG` остаётся одним изменяемым объектом** с теми же ключами и той же размерностью.
   Лаборатория мутирует `CONFIG` в памяти и ожидает, что следующий прогон считается по новым числам.
2. **Никаких производных констант, посчитанных один раз при импорте** из `CONFIG`. Производные
   величины (стоимость, длительности, множители) считаются в момент вызова. Если очень нужно
   кэшировать — кэш обязан сбрасываться при применении уровня (экспортируй `resetDerived()`).
3. **Уровни не применяются автоматически в ядре.** `newGame(seed)` не должен сам накладывать пресет:
   по умолчанию ядро работает с тем `CONFIG`, который ему дали (это «нормальный» уровень и режим
   лаборатории). Применение уровня — явный вызов.
4. **Сигнатуры и семантика** `newGame(seed)` и `tick(state)` — те же. Цикл лаборатории:
   ```ts
   const state = newGame(seed);
   for (let i = 0; i < days; i++) { if (state.bankrupt) break; player.turn(state, stats); tick(state); }
   ```
5. **Детерминизм обязателен**: один сид + один набор значений = один и тот же результат.
   Никакого `Math.random()` в ядре — только RNG от сида (`src/core/rng.ts`).
6. **Headless-режим** обязан жить: `pnpm play` (`scripts/playthrough.ts`) и тесты (`pnpm test`) —
   без UI, без DOM. Уровень не должен требовать браузера.
7. **Ключи `CONFIG`, перечисленные в `difficulty-presets.json`** (`overrides` и `fullConfig`), не
   удалять и не переименовывать без согласования: это тот словарь, которым лаборатория говорит
   с игрой.

## 6. Рекомендуемый интерфейс

```ts
// src/core/difficulty.ts
export type DifficultyId = 'easy' | 'normal' | 'hard';

/** Определение уровней: перекрытия поверх базового CONFIG (данные — из difficulty-presets.json) */
export const DIFFICULTY: Record<DifficultyId, {
  label: string;          // «Лёгкий»
  note: string;           // чем для игрока отличается
  overrides: Partial<typeof CONFIG>;
}> = { /* ... */ };

/** Чистый способ получить конфиг уровня, не трогая глобальный CONFIG */
export function difficultyConfig(id: DifficultyId): typeof CONFIG;

/** Применить уровень к живому CONFIG (с вызовом resetDerived(), если кэши есть) */
export function applyDifficulty(id: DifficultyId): void;

/** Текущий уровень (для сохранений и UI) */
export function currentDifficulty(): DifficultyId;
```

JSON удобно **не копировать руками**, а сгенерировать из него `difficulty.ts` маленьким скриптом
(или импортировать JSON напрямую, если tsconfig это позволяет) — тогда числа обновляются одной
командой, и расхождений между документом и кодом не будет.

## 7. Чего в этих числах нет (прочитать до внедрения)

- **Числа — гипотеза, а не истина.** Их нашёл поиск по метрике; метрика отражает то, каким человек
  видит хороший баланс, и её можно менять. Если в игре числа ведут себя иначе — это повод вернуться
  в лабораторию, а не подкрутить молча.
- **«Перчинка» не измеряется числами**: разброс рецензий, юмор событий, наглость рынка — см.
  `plan/08_Экономика_и_баланс.md` §7. Уровни сложности могут и должны отличаться не только числами
  (например, частотой и злостью событий) — но это дизайнерское решение, а не результат замера.
- **Важное наблюдение по 20 годам:** в текущей экономике длинная партия сильно инфлирует —
  «разумный» игрок к 20-му году накапливает миллиарды ¥, тогда как план (`plan/08`) ставит целью
  «активы свыше 100 млн к Y20». То есть **длинная игра становится слишком щедрой**; лаборатория
  мерила уровни в этом масштабе и подсветила это как открытый вопрос баланса. Если это противоречит
  замыслу — сначала правится экономика (и перезамеряются уровни), а не маскируется уровнями.
- **«Сложный» уровень на двух годах упирается в деньги:** при стоимости разработки 3.2 и капитале
  400K даже «разумный» не дотягивает до нижней границы коридора денег. Либо смягчить перекрытия
  «сложного», либо признать, что на сложном уровне деньги — дефицит по замыслу (и тогда это надо
  отразить в ожиданиях метрики в лаборатории).

## 8. Приёмка (проверяемое)

- [ ] `pnpm typecheck` и `pnpm test` — зелёные.
- [ ] `pnpm play` (headless) проходит партию на **каждом** уровне и не падает.
- [ ] Лаборатория продолжает работать: из `E:/My/gds-autoresearch` команда `pnpm probe` проходит
      (она проверяет, что мутация `CONFIG` в памяти меняет результат прогона — то есть контракт §5 цел).
- [ ] Тот же сид + тот же уровень = тот же результат (проверить дважды один и тот же прогон).
- [ ] Уровень выбирается в UI на старте новой игры, виден игроку и сохраняется в сохранении.
- [ ] Перекрытия уровней действительно применяются: сравнить `START_MONEY`, `DEV_COST_SCALE`,
      `BLACKOUT_CHANCE`, `CONTRACT_WEEKLY_RATE`, `PAYDAY_DAY` на трёх уровнях — они должны отличаться
      ровно так, как в `difficulty-presets.json`.
- [ ] В игре нет скрытых копий конфига: поиск по `CONFIG.` показывает чтение живого объекта, а не
      снимков, сделанных при импорте.

## 9. Как обновить числа (когда случится перезамер баланса)

```bash
cd E:/My/gds-autoresearch
PYTHONPATH= python scripts/export-presets.py      # перезапишет difficulty/difficulty-presets.json
```

Скрипт берёт определение уровней из правил лаборатории (`lab.config.json`), а значения — из текущего
чемпиона серии, и кладёт результат рядом с этим файлом. `source` в JSON всегда говорит, каким
протоколом и каким экспериментом получены числа.
